专用智能体系统设计：流程、提示词与 Harness

通用大模型什么都能聊一点，但做不出能交付的东西。把一个领域专家的工作方式搬进智能体， 靠的是三件彼此咬合的事：流程（把工艺顺序固化成链）、提示词（把专家准则写进角色与契约）、 Harness（用代码把模型一定会犯的错提前挡住）。下面以本项目的「智能硬件设计智能体」为例， 每一节都对应仓库里真实存在的文件与参数。

0开篇：专用化到底在专用什么

给模型一句「帮我设计一台智能硬件」，它会给你一篇漂亮的科普文。要让它交付可制造的东西， 必须把不确定性从三个层面逐个收掉 —— 而且顺序不能反：先定流程，再写提示词，最后才谈 Harness。

① 流程 · Process

专家不是想到哪做到哪，而是有固定工序与交付物。把工序写成阶段链 + 交付契约， 让「先做什么、交出什么文件」成为数据，而不是模型的临场发挥。

对应：agent/stages.py · agent/pipeline.py

② 提示词 · Prompts

五段式结构：角色 → 通用准则 → 交付契约 → 收尾动作 → 回交限额。 准则里每一条都对应一次真实事故，不写「请尽量」，只写硬约束。

对应：agent/subagents.py · main_agent.py

③ Harness · 缰绳

提示词会被长流程冲淡。凡是「错了代价高」的约束，都要下沉成代码： 门禁、幂等锁、预算护栏、人工闸门、重试与降级。

对应：guards / stagestate / hitl / server

一句话心法：提示词负责「希望它怎么做」，Harness 负责「它做不到时系统仍然正确」。 凡是你在提示词里写了第三次还是有人违反的规则，就该下沉成代码。

任务 DNA：先选范式，再谈执行

不是所有需求都值得派六个子智能体跑十五分钟。本系统用三个「基因」做路由 （agent/paradigms.py）：时效基因（能等多久）、 容错基因（错了代价多高）、进化基因（这类任务会不会反复遇到）。 四档范式对应完全不同的执行参数，而不是换个提示词那么简单。

档位范式子智能体工具预算时限适用
leanReAct · 边做边想不派单，自己答30240s查型号、问参数这类短查询
standardPlan-and-Execute6 个全派150900s完整产品设计（默认）
review+ Reflexion 反思6 个 + 返工一轮1801200s高风险词 ≥3 或同类需求踩过坑
explore+ Tree of Thoughts6 个 + 3 方案打分2201500s需求模糊、多目标权衡

降级链固定为 explore → review → standard → lean： 任何一档超时、超预算或工具链断裂，就往下降一档重跑，而不是原地重试 —— 原地重试只会重复失败路径。

三条不能破的边界

边界做法破了会怎样

2流程设计：把工艺顺序写成链

智能硬件的五个阶段不是五份互不相干的文档，而是一条几何与电气双向约束链。 上游产物没落盘就开工，下游只能凭想象填数字 —— 最后评审阶段的「尺寸对不上」， 其实是编排阶段就埋下的。

外观设计10_appearance/
结构设计20_structure/
硬件设计30_hardware/
固件与仿真40_firmware/
交叉评审90_review/
点一个阶段，看它的交付契约、开工门禁与传给下游的硬约束。

约束链：上游的一句话，就是下游的一个数字

从传给下游的硬约束下游若无视
PRD外形尺寸上限、供电方式、成本上限、使用环境外观做出无法量产、装不下电池的形态
外观10_appearance/prompts.json 里可量化的外形描述 + 渲染图结构重新想象一台产品，外观图与结构图对不上
结构CAD 回传的包围盒、内腔净尺寸、安装柱坐标、限高区PCB 板框画大了装不进去；连接器落在壳壁上
硬件板框 → 封装 → 层数的推导；netlist.json 引脚；BOM 器件固件编造引脚号，BOM 上有器件却没人写驱动
固件实际用到的引脚与外设、功耗估算电源树带不动；仿真步骤与实物不符
设计要点：阶段之间传递的必须是可校验的数值，不是「详见图纸」这类话。 本系统里 pipeline.pcb_envelope() 直接把结构尺寸推成板框建议： 内腔减 1mm 单边余量 → 板面积 → 反推封装（0402 / QFN / LQFP）与层数（2 或 4）， 连理由都一起写进提示词。模型不用猜，猜就错。

流程设计的四条经验

① 串行优先，别急着并行

只有依赖真正独立才并行。硬件/固件看似可以并行，但固件要读 BOM 与引脚 —— 强行并行只会让两边各编一套。

② 契约名硬编码

文件名写死（structure.md、netlist.json…）。改名会让交付清单认不出它属于哪一步，用户也就打包不到它。

③ 门禁读磁盘，不读对话

gate() 只看文件在不在、图是不是坏的、人确认了没。模型说「已完成」不算数。

④ 关卡要能重来

用户提修改意见 → 状态回到 revised → 允许且要求重做本阶段。不能重来的流程，人只能推翻重跑。

3提示词设计：五段式 + 事故驱动

本系统的每份子智能体提示词都是同一个骨架。差别只在中间那段「这个专业要交什么」。 统一的骨架让六个智能体的行为可预期，也让「哪一条被违反了」一眼可查。

段落写什么为什么必须有
角色你是谁，你的产出会被谁接着用没有「下游是谁」，模型就会写成自洽但无用的独白
通用准则跨专业一致的硬规则（见下）每条准则背后是一次真实事故，重复成本极高
交付契约必须落盘的文件名 + 每份文件的内容清单没有文件名约束，产物就对不上交付清单，用户打包不到
收尾动作做完必须 confirm_with_user / 必须走哪个兜底靠模型「记得先问一句」，它一定忘
回交限额向主智能体回交 ≤400 字 + 固定字段不限额就会把整份文档贴回主上下文，几轮就爆

通用准则 COMMON_RULES：逐条都是事故换来的

点开任意一条，看它背后的线上事故与修复方式。

主智能体提示词：把「调度者」写成硬约束

主智能体最容易犯的错是「自己下场干活」——它有全套工具时不干才奇怪。 所以提示词里第一条不是「你是总指挥」，而是「你没有这些工具」。 

【你的角色：调度者，不是执行者 —— 这是硬约束】
- 你**没有**出图 / 建模 / 画原理图 / 校验电路 / 生成 BOM 的工具，也拿不到 save_artifact。
  阶段产出物一律通过 task 委派给对应子智能体完成；你自己下场干只会把同一阶段做两遍。
- 你手里的自定义工具只有两个：`stage_gate`（查门禁）和 `confirm_with_user`（请人确认）。

【每个阶段只派一次 —— 重复派单是本系统最常见的失败模式】
- 一个阶段**只能委派一次**。子智能体回交后，用 ls 核对产物是否落盘：
  - 落盘了 → 立刻进入下一阶段（需要人工确认的阶段先 confirm_with_user）。
  - 没落盘 → 让**同一个**子智能体补做（补充指令写清缺哪个文件），不要重新派一个新实例
    从头再来 —— 新实例没有上下文，会把已做好的东西推翻重做一遍。
- 严禁「先派一次看看，再派一次确认」：实测这样会让 PRD 被写两遍、外观图出两遍、
  同一份产品图被请用户确认两次。
子智能体提示词范例：工业设计师（出图链路最难的一段）

出图最怕两件事：同一台产品画出几代外形；以及「图生图」与「文生图」混用。 所以提示词把调用顺序写成了步骤，连「第二张只描述要改成什么样」都写死了。 

【必须出真实渲染图 —— 由 Agnes 出图，且必须串行、前后同源】
工具默认 reference="auto"：第二张起会自动以**上一张产品图**为参考做图生图，
同一台产品不会画出两代外形。

**必须一张一张串行生成，禁止把几个 prompt 攒在一起或并行调用**：
1. 第一次调用 generate_product_image(kind="render")：产品主视角渲染图。
   这张图是后面所有图的**基线**。等它返回、确认文件已落盘后，再进行下一步。
2. 第二次调用 generate_product_image(kind="render")：只描述「要改成什么样」
   （例如「换成 45 度侧视」），**不要重复描述产品本身** ——
   产品长什么样由参考图决定，重写一遍反而会让模型把产品改掉。

【你写的提示词会被结构阶段复用 —— 写准一点】
每次出图用的 prompt 会自动存档到 10_appearance/prompts.json，结构工程师就是拿它去做
3D 建模的形状约束。所以 prompt 里**必须写清可量化的外形信息**：整体形态、长宽高比例、
主色与材质、可见特征（屏幕/按键/接口的位置）。写「科技感十足的小夜灯」这种形容词，
结构阶段就只能瞎猜尺寸。
兜底链：允许失败，但不允许「假装成功」

外部服务一定会失败。与其祈祷，不如把失败写进流程：失败时的产物、 写什么、最多重试几次，全部提前规定。

  • 出图失败：错误含「鉴权失败」→ 立即停止调用（重试多少次都一样）；超时/限流 → 换中性 prompt 重试最多 2 次。
  • 兜底产物：orthographic.svg（手写三视图，离线可出）+ 文档里注明「AI 图不可用，形状以工程视图为准」。
  • 建模失败：照真实报错的行号改，最多 3 次；仍失败就在文档写失败原因 + 参数化尺寸表。
  • 绝对禁止：placeholder / TODO / 「略」这类占位内容，以及伪造尺寸。

提示词写作的六条检查项

  1. 每一条约束都能指出「不这么做会发生什么」—— 指不出就删掉，那是噪音。
  2. 能用代码保证的，不要在提示词里重复第三次（重复说明它该下沉了）。
  3. 给出正例而不只是禁令：写「用 fillet(builder.edges()...）」比「别写错 API」有效。
  4. 把失败路径写出来：什么错该重试、什么错该放弃、放弃时留下什么。
  5. 动作必须有宾语：confirm_with_user(stage="10_appearance") 而不是「记得让用户确认」。
  6. 回交内容定长定字段：≤400 字 + 固定几个要点，主上下文才不会被撑爆。

4Harness 设计：把「一定会犯的错」提前挡住

这一节是本报告的核心。下面七个部件，每一个都对应一句「提示词里写了但还是有人违反」的规则。 它们共同的原则是：判据读磁盘、读状态文件，不读模型的自我声明。

4.1 工具白名单：从能力上杜绝越权

角色拿到的工具设计意图
主智能体 stage_gate、confirm_with_user、write_todos、task、内置只读文件工具 它只能查状态、派单、请人确认。想干活？只能派单。
子智能体 全部 12 个领域工具（出图 / CAD / 电路校验 / BOM / 网表 / 门禁 / 确认） 专业活由专业角色干，上下文隔离，只回交结论。 
# agent/main_agent.py
# 主智能体只拿「调度用」的自定义工具 —— 出图/建模/校验一律不给它。
# 线上事故：主智能体拿着全套工具自己下场调 text_to_cad 建模，而子智能体也在建，
# 同一阶段被做两遍，预算烧光跑到 5/6 阶段就被迫中止。
MAIN_TOOLS = [stage_gate, confirm_with_user]

4.2 阶段门禁 gate()：磁盘是唯一权威

每个子智能体开工第一步不是「开始设计」，而是 stage_gate("自己的阶段")。 它返回三件事：能不能开工、缺什么、上游传下来哪些硬约束。

阶段门禁额外判据拦住的典型错误
20_structure外观图存在且不是坏图（11 字节的 placeholder 会被识别）拿假图建模，整条链报废
30_hardware能从 consistency.md 读到外形尺寸，并自动推板框/封装/层数板框画大装不进去
40_firmware存在 netlist.json 或 bom.csv编造引脚号写驱动
所有下游外观 / 结构必须已有用户确认记录没人看过的外观一路跑到评审
门禁的价值不在于「拦」，而在于拦的时候告诉模型该干什么。 返回里带着 missing 与可执行建议（「请先调用 confirm_with_user(stage=…)」）， 模型才能自我纠偏，而不是卡死或硬闯。

4.3 幂等状态机：让「同一阶段做两遍」在工具层做不成

提示词里写「不要重复做」在长流程里必然失效。所以把每个阶段的状态落到 XX_stage/_stage.json，并让昂贵工具在开工前先问一次这个状态。 

# agent/stagestate.py —— 昂贵工具开工前的幂等闸
EXPENSIVE_TOOLS = {
    "generate_product_image": "10_appearance",   # 出图：贵，且会覆盖已确认的基线图
    "text_to_cad":            "20_structure",    # 建模：贵，下游全靠它
    "render_schematic":       "30_hardware",
    ...
}

def guard(root, sid, tool, files=None) -> str:
    """返回空串 = 放行，非空 = 拒绝理由（直接回给模型）。"""
    d = load(root, sid)            # 读 XX_stage/_stage.json
    if d["status"] in (PENDING, WORKING, REVISED):
        return ""                  # 没做过 / 正在做 / 用户要求改 —— 放行
    if d["status"] == CONFIRMED:
        return (f"⛔ {sid} 本阶段产物已生成并经用户确认，不要再调用 {tool} 重做一遍。"
                "\n重复执行会覆盖已确认的产物、烧掉预算，并把同一份东西再请用户确认一次。")
只对「贵且会覆盖产物」的工具上锁。文档写入（补一份漏写的 md）不锁 —— 补文档是合理的，重出一张 700 KB 的渲染图不是。锁得太狠会把正常迭代也挡住。

4.4 人工确认闸门：让流程真的停下来等人

外观图出来长什么样、结构能不能装，只有人看了才算数。这两个阶段做完必须挂起整条流程， 等用户在界面上确认或填修改意见。而且等待不计入运行时间，不会把一次等人变成一次超时。

交互演示：模拟一次 confirm_with_user(stage="10_appearance", rounds=N)

等待调用…
去重是必须的。实测一次运行里同一个确认被挂起等待了三次（14.7s / 101s / 24.7s）。 现在按 rounds 判重：同一轮重复调用直接返回上一次结论，不再阻塞； 轮次 +1 才真正等待。

4.5 护栏：预算、停滞与重复调用

同一个需求跑两次，事件数 8 万 vs 34 万、工具 72 次 vs 239 次 —— 差异不是随机的。 没有预算的自主循环，模型可以连续思考十几分钟不落一个产物，也能把同一个工具用同样的参数反复调上百次。

预算模拟器：按「代价」加权，而不是按次数

拖动滑块，看一次运行在 standard 档（预算 150）下消耗了多少。只读调用按 0.1 计， stage_gate 这类纯磁盘判据也是 0.1，出图 / CAD 按 1.0 计。

—

对比：若所有调用都按 1.0 计，同样的行为会消耗 — 次 —— 这正是早期版本 80 次预算跑到 5/6 阶段就中止的原因。

护栏判据为什么这样定
停滞中止距上次「实质进展」超过 120s 才算空转时间本身不是失败信号，停滞才是。实测一次运行 904s 被砍，产物明明还在增加
进展定义只有写类工具成功 / 磁盘出现新产物才算只读返回值不算进展 —— 否则「反复回读自己写的报告」会被判成在前进
重复调用只读 24 次 / 同一文件 10 次 / 参数抓不到时 15 次分档阈值：只读幂等无副作用，误杀成本远高于写类工具
参数签名args 不完整（空串 / 半截 JSON / 占位 {}）时挂起等待再判流式工具调用的 args 首发常为空，拿它当去重键会把读 5 个不同文件算成重复 5 次
超时续期到点但仍在进展 → 自动延长 600s；真到硬上限 → 按阶段存盘点自动续跑（最多 2 轮）硬墙会把「正在稳定产出」的运行砍掉；续跑复用同一工作区，从下一个未完成阶段接着做
中止的定性要和交付状态挂钩。产物已够时按「目标达成」收尾，别显示「超出预算中止」—— 东西都在却报失败，比真失败更伤信任。本系统里这是 RunGoal 异常， status="done"，error 字段留空。

4.6 网络层：区分「断了」与「排队」
