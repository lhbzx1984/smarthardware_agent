# 网关限流（429）定位与修复 · 2026-10-13

## 1. 现象

每次跑任务都反复弹出：

```
网关限流（429），等待 50 秒后自动续跑（第 3/4 次）。已落盘的产物会保留，不会从头重来。
```

用户反馈：以前跑没有这个，而且很快就完成。

## 2. 定性：不是网络抖动，是**免费额度的 token 窗口被打满**

分层实测（同一 key / 同一网关）：

| 探测 | 结果 | 结论 |
|---|---|---|
| 串行 5 次小请求 | 全 200，0.7~1.2s | 不是请求频率限流 |
| 并发 2 / 3 个小请求 | 全 200 | 不是并发数限流 |
| 单轮 16k 字符请求 | **429** | 与体积相关 |
| 额度耗光后 2000 字符请求 | **429** | 与体积无关，是**窗口累计** |
| 等待后再发小请求 | 200 | **滑动窗口**，等一会就恢复 |

429 响应体原文：

```json
{"error":{"message":"You've reached the API rate limit for free users. Upgrade to a Token Plan..."}}
```

**所以：免费额度按时间窗口内的 token 总量限流，撞了要等窗口滑过去。**

## 3. 谁吃掉了额度：thinking 输出占 75%~85%

从事件流统计三次 run 的输出字符数：

| run | thinking | 正文 token | 占比 |
|---|---|---|---|
| 1fb97370ea41（1040s 跑完） | 1,057,955 | 351,227 | 75% |
| 2bb9021f26e0（1411s 跑完） | 893,086 | 159,273 | 85% |
| 96e3b9a15712（跑到外观中断） | 616,861 | 140,940 | 81% |

一次完整 run 输出 **100 万+ 字符**，其中八成是思维链。

### 为什么关不掉：`AGENT_THINKING=0` 是个纸面开关

`main_agent.get_model()` 里关闭分支写成：

```python
body: dict[str, Any] = {}
if want_thinking:
    ...
# else：body 保持空 dict，什么参数都不发
```

**不发参数 ≠ 关闭思考** —— 网关按自己的默认值走，实测照样吐思维链。

对照实测（同一问题，`max_tokens=500`）：

| | reasoning | 输出 token | 总 token | 耗时 |
|---|---|---|---|---|
| 不传参数 | 310 字 | 226 | 528 | 5.0s |
| `{"thinking":{"type":"disabled"}}` | 83 字 | **103** | **405** | 2.5s |

输出 token 省 **54%**，耗时减半。

## 4. 修复

### 4.1 显式关闭思考（`providers.disabled_thinking_body`）

```python
else:
    body = providers.disabled_thinking_body(model)   # 此前是空的，等于没关
```

各家字段名不统一（Qwen 用 `enable_thinking`、GLM 用 `thinking.type`），按模型名适配；
认不出的退回最通用的 `{"thinking": {"type": "disabled"}}`（未知字段网关一般忽略，不会报错）。

### 4.2 配额守卫：把"撞了再退避"改成"快撞了先慢下来"（新增 `agent/quotaguard.py`）

撞一次 429 要退避 25~75 秒；而在请求前主动等几秒让窗口里的旧记录滑出去，成本低一个数量级。

- 滑动窗口记账：langchain 回调按真实 `usage_metadata` 累计，拿不到就按字符估算（中文 1 字≈1 token，其余 4 字符≈1 token，**宁可高估**）
- 请求前限速：钩在 `ReasoningChatOpenAI._generate` / `_stream` 上。回调是在请求**已经发出**时才触发的，拦不住；要卡就得卡在发请求之前
- 撞到 429 后 `penalize()`：把窗口记满 + 设惩罚静默期。不记满的话下一个请求还会按原节奏再撞一次 —— 这正是"每次都弹限流提示"的来源
- 自动降级：撞过 429 后 `thinking_off` 为真，后续请求自动改成关闭思考

可调参数（`.env`）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `AGENT_QUOTA_GUARD` | 1 | 总开关，0 = 退回老行为 |
| `AGENT_QUOTA_WINDOW` | 60 | 窗口秒数 |
| `AGENT_QUOTA_WINDOW_TOKENS` | 40000 | 窗口预算 |
| `AGENT_QUOTA_PENALTY` | 20 | 撞 429 后的静默期 |
| `AGENT_QUOTA_MAX_WAIT` | 20 | 单次主动等待上限（不能让界面看起来卡死） |

### 4.3 429 分支接入惩罚

`server._run_with_retry()` 判定为限流时调 `quotaguard.penalize()`，再走原有退避。

## 5. 过程中自己踩的坑：可重入锁

`QuotaGuard.wait_before()` 持锁时调用了 `self.used()`，而 `used()` 也要同一把
`threading.Lock` → **当场死锁**。表现是：任务停在"已注入相似历史需求经验"之后，
第一个 LLM 调用永久不返回，界面毫无反应，日志也没有任何报错。

定位手段：`faulthandler.dump_traceback_later(50, exit=True)` 直接打印卡住时的线程堆栈：

```
File "quotaguard.py", line 52 in used
File "quotaguard.py", line 114 in wait_before
File "llm.py", line 49 in _throttle
File "llm.py", line 54 in _generate
```

改 `threading.RLock()` 解决。**教训：一个方法内部调用同类其它公开方法时，要么用可重入锁，
要么拆出不带锁的私有实现。**

另外加了一个保护：单次请求估算就 ≥ 整个窗口预算时直接放行 —— 等也没用，窗口滑出去它还是超。

## 6. 修复前后对比

同样跑 ~300 秒：

| run | 事件数 | thinking 字符 | token 字符 | 429 次数 |
|---|---|---|---|---|
| 修复前 `96e3b9a15712` | 258 | 616,861 | 140,940 | **5** |
| 修复后 `b5258537540f` | 106 | 264,708 | 86,028 | **0** |

thinking 输出降 57%，429 归零。

## 7. 给使用者的说明

- **深度思考默认关闭**（`AGENT_THINKING=0`）。想看推理过程就在前端设置里打开，但免费额度下会明显更容易撞 429。
- 换服务商/升级 Token Plan 是根治办法；免费额度下只能靠省输出换稳定。
- 若仍偶发 429，说明窗口预算估得偏松，把 `AGENT_QUOTA_WINDOW_TOKENS` 调小（如 24000）会更保守、更慢但更稳。
