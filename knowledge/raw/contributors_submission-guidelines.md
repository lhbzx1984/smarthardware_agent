# Submission Guidelines & Acceptance Criteria
Anyone with a Cirkit account can submit a component for consideration for the
public library. Public components must meet our quality standards so the
community can use them confidently. The best way to understand our expectations
is to study our existing high-quality components.
Submitting a component does not guarantee publication. Cirkit may accept the
submission, request changes, or decline it after review. High-quality accepted
components may also be featured on the Cirkit homepage.
## Follow Our Examples[#follow-our-examples](#follow-our-examples) ​
Your component should meet the same standards as our published examples. Study these implementations for code structure, documentation style, and testing patterns:
- [/docs/custom-simulation-parts/component-examples](/docs/custom-simulation-parts/component-examples) Component Examples - Browse our library of example components with full source code
- [/docs/tutorials/create-simulation-servo](/docs/tutorials/create-simulation-servo) Servo Component Tutorial - Complete walkthrough of building a servo component
- [/docs/tutorials/create-simulation-lcd](/docs/tutorials/create-simulation-lcd) 16x2 LCD Display Tutorial - Example of a complex display component
- [/docs/custom-simulation-parts/getting-started](/docs/custom-simulation-parts/getting-started) Getting Started Guide - Foundation concepts and patterns
Right-click any simulatable component in Cirkit Designer, select "Edit a copy of Component," and navigate to the simulation tab to see detailed implementation examples.
## Quality Standards[#quality-standards](#quality-standards) ​
### Code Requirements[#code-requirements](#code-requirements) ​
- Clean, readable code with clear variable names and logical structure
- Comprehensive comments explaining complex logic and calculations
- Error handling for invalid inputs and edge cases
- Performance optimization - components must run smoothly in real-time simulation
### Simulation Accuracy[#simulation-accuracy](#simulation-accuracy) ​
- Realistic behavior that matches the real-world component
- Proper parameter ranges with appropriate defaults
- Accurate timing and response characteristics
- Electrical properties modeled correctly (voltage, current, resistance, etc.)
### User Interface[#user-interface](#user-interface) ​
- Intuitive controls that follow existing Cirkit patterns
- Clear labeling of all parameters and connections
- High-quality component image - preferably upload an SVG or Fritzing fzpz part file as the image source
- Consistent styling with existing components
## Documentation Standards[#documentation-standards](#documentation-standards) ​
### Example Project Required[#example-project-required](#example-project-required) ​
Every submission must include an example project that:
- Demonstrates core functionality of your component
- Shows realistic usage in a practical circuit
- Tests key features and parameter ranges
- Works correctly without errors or warnings
## Testing Requirements[#testing-requirements](#testing-requirements) ​
Before submitting, verify your component:
- ✅ Works in example projects - included demonstration works perfectly without errors
- ✅ Handles edge cases - invalid inputs, extreme parameter values
- ✅ Works with other components - integrates properly in complex circuits
- ✅ UI responds properly - all controls work as expected
- ✅ No errors - no console warnings or JavaScript errors
## Acceptance Criteria[#acceptance-criteria](#acceptance-criteria) ​
Your submission will be evaluated on:
- Code Quality - Clean, well-documented, performant code
- Simulation Accuracy - Realistic component behavior
- User Experience - Intuitive interface and clear documentation
- Working Example - Component works correctly in provided example project
## Review Process[#review-process](#review-process) ​
- Initial screening - Check for basic functionality and completeness
- Code review - Evaluate code quality, structure, and documentation
- Simulation testing - Verify accuracy and performance in various scenarios
- User experience review - Test interface usability and documentation clarity
- Final decision - Accept, reject, or request specific improvements
